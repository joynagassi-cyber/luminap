# Receipt — RBAC chantier D : preuve E2E rôle+org+capacités par les 4 transports

- **Date** : 2026-10-27
- **Branche** : `agent/rbac-e2e` (PR #63, mergée)
- **Tâche** : prouver, par le test, que quel que soit le transport d'invitation,
  l'invité reçoit le **rôle cible**, l'**organisation cible** et les
  **capacités** de l'invitation.
- **Statut** : **terminé**

## Livrable

`src/capabilities/__tests__/invitation-rbac-e2e.test.ts` — 15 tests.

Les **4 transports réels** sont exercés sur le même moteur :
1. code manuel `LUM-XXXXXX` ;
2. payload QR (`buildQRPayload` → JSON → `parseQRPayload`) ;
3. collage de payload ;
4. fichier `.json` (`importInvitationFromFile`).

Le cœur testé est du **vrai code pur, sans mock** : `generateCode`,
`buildQRPayload`, `parseQRPayload`, `importInvitationFromFile`,
`evaluatePermission` (miroir TS de `has_permission`). Seul `@/lib/auth`
(dépendance d'infrastructure qui exige les variables Supabase) est neutralisé.

## Ce qui est prouvé

- Le payload transporté porte `target_role`, `org_id`, `grants_payload`,
  `tags_payload` **sans perte**, et le round-trip reconstruit le même objet.
- La décision correspondante (`evaluatePermission`) : rôle ANCIEN autorisé
  (`reason='role'`), capacité supplémentaire autorisée (`reason='grant'`),
  refus sans la capacité, priorité du `deny` explicite.
- De bout en bout : un payload QR transporté produit rôle+org+capacités, puis
  autorise l'action.

## Limite

La matérialisation serveur (trigger `settle_invitation_claim`) est reproduite
par une projection pure dans le test, pas exécutée en base : le test prouve la
**cohérence de bout en bout du contrat**, pas l'exécution Postgres (couverte
séparément par les migrations du chantier A).
