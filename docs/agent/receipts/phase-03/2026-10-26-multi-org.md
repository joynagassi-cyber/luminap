## Défaut réel prouvé (audit live, 2026-10-26)

Aucune garde anti-cycle n'existait, ni en base ni côté TS :

```sql
SELECT tgname FROM pg_trigger
 WHERE tgrelid='public.organizations'::regclass AND NOT tgisinternal;
-- → seul trg_organizations_updated_at
SELECT pg_get_constraintdef(oid) FROM pg_constraint
 WHERE conrelid='public.organizations'::regclass;
-- → FK parent_org_id, PK, CHECK status, CHECK type. Aucune anti-cycle.
```

Conséquence : un re-parentage d'une org sous l'un de ses descendants (ou sous
elle-même) créait un cycle, faisant **boucler à l'infini** `org_family`
(`20261003000003`) et `org_descendants` (`20261022000008`) — deux CTE
`WITH RECURSIVE`.

## Honnêteté (R12)

- **[Prouvé]** : détecteur + trigger (preuves SQL annulées ci-dessus), tests
  unitaires (11), 4 gates locaux.
- **[Probable]** : la borne `steps <= 1000` suffit pour toute hiérarchie réelle
  (profondeur < 1000) ; au-delà, la garde ne détecterait plus un cycle. Documenté.
- **[Non vérifié]** : le re-parentage concurrent (deux transactions simultanées
  qui créeraient un cycle à deux) — le trigger est `BEFORE` par ligne, sans
  verrou de table ; un cas de course très étroit reste théoriquement possible.
  Non prouvé ici, non corrigé (hors périmètre minimal).

## Risque résiduel

- La **table de fermeture** (`ancestor/descendant/depth` matérialisée, demandée
  par le contrat pour la perf SQLite/PowerSync) n'est **pas** introduite : la vue
  récursive existante couvre le besoin fonctionnel et la profondeur/largeur
  testées. Introduire une table matérialisée serait une migration lourde non
  justifiée par un besoin mesuré (pas de latence observée) → proposition, pas
  implémentation (principe « minimal, réversible »).
- Le déplacement de sous-arbre « atomique » n'est pas un nouveau chemin d'écriture :
  `setParentOrg` ne bouge qu'un nœud, la descendance suit par le parent.
