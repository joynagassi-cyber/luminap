# Receipt — Phase 7 (Finance)

- **Date** : 2026-10-26
- **Branche** : `agent/phase-07-finance`
- **Périmètre** : modèle de transaction / contrepassation / suppression dure.
  Deux défauts critiques trouvés par audit live (base de dev).

## Défaut 1 — R101 : le flux finance est cassé au niveau base (CRITIQUE)

`notify_transaction_change()` (migration `0012`, toujours active) insère dans
`notifications` en listant **6 colonnes** mais ne fournit que **5 valeurs** : le
`message` manque. Toute écriture d'une transaction PENDING/APPROVED/REJECTED
échoue en `42601: INSERT has more target columns than expressions`.

**Preuve** (transactions annulées) :

| Opération | Avant | Après |
|---|---|---|
| `INSERT status='PENDING'` | **42601** | OK + notification |
| `UPDATE DRAFT→APPROVED` | **42601** | OK + notification |
| `DELETE` | (branche NEW=NULL) | OK + notification |
| `INSERT status='DRAFT'` | OK (garde fausse) | OK |

**Impact** : aucune transaction ne peut être soumise ni approuvée (UI, PowerSync,
API). La finance et ses rapports sont inopérants. Défaut latent : la table
`transactions` était vide sur l'instance dev.

**Correctif** : `20261026000003_fix_notify_transaction_change.sql` — fournit le
`message` par cas et gère DELETE via `OLD`.

## Défaut 2 — R102 : suppression dure d'une transaction APPROVED (HAUTE)

`transactions_delete` est `is_org_member(...)` : tout membre peut supprimer une
transaction APPROVED. Le garde-fou « APPROVED = immuable » n'existait que côté
client (`deleteTransactionPS`) ; PowerSync écrit en service role (RLS
contournée) et l'API REST n'applique pas la logique TS.

**Preuve** (annulée) : un profil `MEMBRE` a supprimé une transaction `APPROVED`.

**Correctif** : `20261026000004_guard_approved_transaction_delete.sql` — trigger
`BEFORE DELETE` levant `TRANSACTION_APPROVED_IMMUTABLE` (P0001) pour APPROVED.
DRAFT/PENDING/REJECTED restent supprimables (parité `deleteTransactionPS`) ; la
contrepassation reste le mécanisme sanctionné.
